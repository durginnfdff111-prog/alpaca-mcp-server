# Crash Guard — paper-only gateway (Phase 1, no order submission)

## What this branch does
- Adds `alpaca_mcp_server.crash_guard`: standalone deterministic risk model.
  - volatility-targeted sizing: 12% annual vol target / last 20 daily log returns
  - drawdown brake: 10% -> 50% of base size; 15% -> 25%; 20% -> no new risk; 25% -> hard halt
  - 50/200 SMA trend filter
  - quarter-Kelly fraction + 10% per-position weight cap
- Adds `preview_crash_guard`, a read-only MCP tool that evaluates **hypothetical,
  caller-provided data**. It always returns `execution_authorized=false`,
  `submitted=false` even if its pure mathematical model reports `approved=true`.
- Refuses to construct this server for live Alpaca base URLs.
- At the shared Alpaca trading HTTP client, **blocks ALL mutating methods** before
  the network call (order POST; order PATCH; options exercise; DELETE close
  position; cancellations; configuration changes; etc.). This protects both
  hand-crafted order overrides and autogenerated OpenAPI tools.
- No Railway environment variable, service, deployment, or GitHub `main` is
  modified. This is a development-branch safety layer, **not a live bot**.

## Limitations and evidence needed for Phase 2
1. The referenced `https://hft.md/crash/llms.txt` could not be fetched,
   so the values above are provisional and **not attributed to the file**.
2. Hypothetical equity, peak equity, candles, probabilities and payoff ratio
   are **not verified**. These calculations are not permission to trade.
3. Future brokerage integration must obtain paper account equity from Alpaca
   and use a cash-flow-corrected high-water mark; must validate at least 200
   complete adjusted session bars, their freshness and session boundaries.
4. Kelly inputs require a sufficiently large, recorded, out-of-sample set of
   executed **strategy** trades; absent validated statistics => no new buys.
5. The risk model currently sizes one new position in isolation; future
   integration must subtract existing positions and open orders, enforce a
   portfolio risk budget, prevent shorts/leverage and handle stale prices,
   venue-specific constraints, parallel-order races and idempotency.
6. The no-write hook deliberately blocks even risk-reducing actions. This
   is a simulation-only phase, not a usable emergency liquidation mechanism.
7. No paper broker order was submitted. An actual paper-order pilot would
   require separate explicit approval and complete review of those controls.

## Test
`pytest tests/test_crash_guard_paper.py`

The CI core job executes this suite without secrets. The secret-backed
paper integration job is **manual workflow_dispatch only**, so a pull request
cannot accidentally place paper orders.

## Release gate
1. Run the complete CI test suite on this exact branch; capture run IDs and logs.
2. Verify the paper endpoint AND paper credentials using read-only account
   calls, with secrets redacted and no broker mutations.
3. Verify authoritative paper equity, cash-flow-adjusted peak, adjusted
   daily bars, open orders and positions; reject missing/stale data.
4. Verify out-of-sample Kelly statistics and portfolio-wide exposure limits.
5. Review emergency cancel/close handling separately; the current blanket
   mutation blocker must NOT be described as a production liquidation guard.
6. Obtain explicit approval for any paper order pilot; never auto-enable
   live orders or merge/deploy this draft without review.
